## Verdict

The AI plumbing (proxy, CSP strategy, consent gates, sanitising) is sound. The failures were
**three specific bugs** that combine into exactly the reported symptoms — "the style formatter
doesn't work, and when it works, Apply doesn't work" — plus a handful of dead/inconsistent
wiring around them.

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | **Critical** | **Apply on a selection silently did nothing.** `<dialog>.close()` hands focus back to the AI menu button — *not the editor* — and `document.execCommand()` is a no-op unless the editor holds focus. The selection apply paths never re-focused or restored the selection. | **Fixed** |
| 2 | **Critical** | **Notes over ~30k characters killed the button with no dialog and no error.** The truncation warning callbacks called `fmtWords()` — a function referenced 8 times but *defined nowhere* — and threw a `ReferenceError` *outside* every try/catch, so Smart Formatting / Tone Rewrite died silently. | **Fixed** |
| 3 | **High** | **Oversized full-note runs destroyed content.** Input was truncated to 30k chars, but the apply path did `selectAll` + insert — replacing the *whole* note with a partial rewrite of its first chunk. | 4 | **High** | **Proxy 403'd legitimate requests on non-standard ports.** The same-origin fallback compared `parse_url($origin)[host]` (no port) against `HTTP_HOST` (often `host:port`) — every AI call failed on `localhost:8787`, preview hosts, and any port-bearing deployment. | **Fixed** |
| 5 | **Medium** | **php-wasm dev/preview can never reach AI providers** (`file_get_contents` has no outbound network), so the AI features were untestable outside production. | **Fixed** — dev-only Node fetch bridge in `dev-server.mjs` |

| 8 | Low | Dead code: `hasFeatureAck`/`setFeatureAck`/`KEY_FEAT_ACK` never used; header docblock described a per-feature prompt that doesn't exist; loading spinner could leak on unknown selection actions. | **Removed/guarded** |

## Addendum (same day) — field reports: "Unexpected token '<'" and "empty response"

Live probe: `GET https://npad.ir/api/ai-proxy.php` → `{"error":{"message":"Method not allowed"}}` —
the proxy is deployed and executing. Both reported errors therefore come from **what the upstream
provider answers**, which the old code forwarded and parsed blindly:

| Report | Root cause | Fix |
|---|---|---|
| `AI error: Unexpected token '<', "<!doctype"… is not valid JSON` | The proxy forwards the upstream's status **and body** unchanged. A Base URL pointing at a website (wrong path, missing `/v1`, provider homepage) answers **200 + HTML**, and the client crashed in `response.json()`. | Proxy (PHP + dev bridge) now **rejects non-JSON upstream replies** with a 502 naming the content-type and a snippet; client detects HTML replies and shows the Base-URL hint for any status. |
| `AI returned empty response` (site default) | Upstream answered 200 + JSON with no `choices[0].message.content` — reasoning models that spend the whole budget on thinking (`finish_reason: "length"`, `reasoning_content` set), legacy `choices[0].text` shape, or non-OpenAI shapes (Gemini `candidates`). | Client now diagnoses each case with a specific message, surfaces provider error bodies even on HTTP 200, and accepts the legacy `text` shape. |

Also added: `max_completion_tokens` alongside `max_tokens` (OpenAI o-series reject `max_tokens`;
other providers ignore the extra key).

New strings (EN/FA): `ai.html_response`, `ai.empty_length`, `ai.reasoning_only`, `ai.wrong_shape`.

**Deployment note:** npad.ir still serves the pre-fix build. These fixes (and everything above)
take effect only after this branch is merged/deployed.

## Addendum 2 — dashboard test showed "✓ Connected! replied: (empty)" and provider billing errors

Root causes found on the live reports:

1. **The dashboard test button had the old parsing.** `admin/ai-panel.js` kept its own
   `data.choices[0].message.content || '(empty)'` success path — a reasoning model that
   produced zero text was reported as a green "Connected!". The response parser now lives in
   **`assets/js/ai-parse.js`** (single source of truth): `ai.js` (features + settings test) and
   `admin/ai-panel.js` (dashboard test, now an ES module) share it, so an empty reasoning-only
   reply shows *"The model returned only internal reasoning… use a standard chat model"*
   instead of a false ✓.
2. **Provider errors now carry status + code.** Billing failures render as
   `AI provider error (HTTP 402) [insufficient_balance]: Insufficient Balance` — the exact
   provider words plus the account-level context, so the key/account being billed is
   unambiguous. (A "credit" error is the provider's own verdict for the key in use — if your
   custom provider key works but the site default errors, they are different keys/accounts;
   update the site default in the dashboard or keep using your own credentials.)
3. Test requests now send `max_tokens: 32` (+ `max_completion_tokens`) so short replies are
   never truncated by the old 5-token budget.

**Deployment note:** still undeployed — npad.ir serves the pre-fix build until this branch is
merged/released.

## Addendum 3 — the "finish reason length" error with a reasoning model configured

The diagnostic did its job: the screenshot proves the new build is deployed and the provider
answers 200 + `finish_reason: "length"` with empty content — the signature of a
**reasoning/"thinking" model** (deepseek-reasoner, R1/QwQ, Gemini-2.5-thinking, OpenAI
o-series/gpt-5) that spends the feature's small token budget (40–4000) on hidden reasoning
before writing anything. Instead of only explaining, the app now **works with those models**:

- `assets/js/ai-parse.js` gains `requestChatCompletion()` — the one request path used by the
  editor features, the settings test and the dashboard test:
  1. model names that look like reasoning models (`deepseek-reasoner`, `r1/rN`, `o1/o3/o4`,
     `qwq`, `*think*`, `gpt-5`) start with a **2048-token floor** instead of the feature's
     tiny default;
  2. if the reply is still empty-length, it **retries once automatically** with
     `min(16384, max(4096, 8x))` tokens — enough headroom for real thinking;
  3. strict OpenAI reasoning models (o-series, gpt-5) get **no custom temperature** (they
     reject it with a 400).
- The guidance error remains as the final fallback (persistent empty-length after retry).

24 AI-suite checks (346 total) pass, including: retry-succeeds, retry-then-fail,
reasoning-name budget floor, and o3-mini temperature omission.

## Addendum 4 — direct apply (no confirmation) with undo/redo

Per product decision: AI actions that only preview + confirm now **apply directly**, reversible
through undo/redo. Option-based features keep their modals.

**Now direct (no result dialog):**
- Smart Formatting (selection or full note) → sanitized result inserted immediately
- Tone Rewrite — the tone *picker* stays (it is a real option), the result dialog is gone
- Extract To-Dos → checklist appended immediately
- Summarize (menu + selection toolbar) → summary note created immediately
- Selection toolbar Rewrite / Shorten / Expand / Translate → inserted immediately

**Still modal (by design):** Smart Title picker (choose between three), word replacement
(choose a synonym), AI Settings, and the one-time data-send consent.

**Reversibility:** every in-editor apply first snapshots the note content into an AI history
stack (`ai.js`). The editor's existing Undo/Redo toolbar buttons (and Ctrl+Shift+Z path) route
through this stack while it has entries — one step back/forward per AI action, since native
undo cannot reliably span the async replacement. After each apply, a success toast offers an
inline **Undo** button that flips to **Redo**. Note-creation (Summarize) is reverted by
deleting the created note via the same toast control.

New strings (EN/FA): `ai.applied`, `ai.note_created`, `ai.todos_inserted`, `ai.undone`,
`ai.undo`, `ai.redo`. New CSS: `.ai-applied-toast__*`. Tests: 27 AI checks / 349 total,
covering direct apply, undo/redo restore & re-apply (stacks and toast buttons), and that the
title picker modal still works.

## Addendum 6 — Text → Table (AI menu)

New AI action "Convert to Table" (`ai-text-to-table`): select a statistical
or delimited passage → the AI menu entry converts it into a real editor
table (thead/th + tbody/td, scope attributes), replacing the selection,
reversible via the AI undo/redo + toast.

Rejection is double-gated, per product decision:
1. **Before the call** — `looksTabular()` refuses obvious prose locally
   (zero tokens spent). Unicode-aware: Persian/Arabic digits (`\p{Nd}`),
   ٪/درصد/میلیون units, `|`/`;`/tab delimiters.
2. **After the call** — the model must answer with one Markdown table or
   exactly `NOT_TABLE`. The reply is re-parsed by `parseMarkdownTable()`
   (GFM shape, separator row required, width-bounded 2–20 columns, cells
   escaped via textContent); any prose/fence-only/garbage reply, or a
   NOT_TABLE verdict, shows the same actionable rejection message.

The table DOM is built locally (`buildTableElement`) — model HTML is never
trusted — and passes the paste-time sanitizer rules on save/export.

New strings EN/FA: `ai.text_to_table`, `ai.text_to_table_needs_selection`,
`ai.text_to_table_not_tabular`. Tests: happy path (Persian digits/units →
table + undo), prose pre-rejection (no fetch), NOT_TABLE reply, non-table
reply, no-selection guidance. 356 passed, 0 failed.

## Addendum 7 — Text → Table hardening (self-review pass)

Stress-tested the feature against an 11-case matrix before anyone hit it in
production. Found and fixed:

1. **`looksTabular` gap — pure numeric columns**: a column of bare figures
   (`۱۲۳/۴۵۶/۷۸۹`, years, amounts — no text labels) was rejected. Such a
   column IS tabular; the heuristic now also accepts selections where
   ≥60% of lines carry numbers. The 2-line-prose-with-dates case still
   routes to the model gate by design (loose pre-gate, final verdict
   server-side).
2. **Single-column tables were impossible**: the parser required ≥2
   columns (`width < 2`), rejecting `| مقدار |`-style replies — exactly the
   shape a numeric column produces. Minimum width is now 1.
3. **Absurd-reply guard**: a model hallucinating 500+ rows is refused
   instead of freezing the editor.
4. **Placement parity with insert-table**: browsers can nest an inserted
   table inside a paragraph/list/cell; the result is now lifted to a
   top-level child of the editor (mirroring `insertTableFromOptions`), a
   spacer paragraph is added below, and the caret lands in the first cell.

Tests: 11-case heuristic matrix locked in + pure-numeric happy path,
600-row refusal, nested-in-paragraph lift. 359 passed, 0 failed.

## Addendum 8 — AI selection popup re-appearing after toolbar clicks

**Report:** selecting text shows the floating AI popup; clicking a button on
the main toolbar hid it for a frame and then **popped it back up**.

**Root cause:** the editor's formatting buttons `preventDefault()` mousedown
so focus never leaves the contenteditable — which also **keeps the text
selection alive**. The document-level `pointerup` handler then re-ran
`handleSelectionAI`, saw the intact selection, and re-surfaced the popup
above the button that was just clicked.

**Fix:** the popup is surfaced **once per selection**. `handleSelectionAI`
now fingerprints the live selection (endpoint nodes/offsets + text prefix,
cleared on every collapse) and skips re-showing while it is unchanged;
a genuinely new selection — or re-selecting after a collapse — brings the
popup back. Applies to every re-evaluation source (toolbar buttons, menus,
dialogs), not just the format toolbar.

Tests: a 6-step scenario (show → outside pointerdown hides → re-evaluation
must stay hidden → repeated clicks stay hidden → new selection re-shows →
collapse + re-select works). Plus a `__resetSelectionToolbarForTests` seam
for the popup singleton. 360 passed, 0 failed.

## Addendum 9 — the model decides tabular-ness; popup gate redone

**1. Text → Table: local pre-check removed (field report: statistical
prose rejected).** A single flowing paragraph full of statistics
(percentages of surveyed students) was refused before the AI ever saw
it — the `looksTabular` heuristic required multiple *lines*, and prose
is one line. Per product decision the heuristic is deleted entirely:
**the model decides** whether the text is table-shaped (the prompt asks
it to find table-shaped data even inside flowing prose, and to answer
`NOT_TABLE` otherwise). The strict Markdown-table parser remains the
hard gate against garbage replies. The rejection copy now reflects the
AI verdict. Trade-off accepted: non-tabular selections cost one API
call before being refused.

**2. AI selection popup: the fingerprint fix was insufficient.** Formatting
commands (`bold`…) split text nodes, so the selection fingerprint changed
across the click and the popup re-surfaced anyway. The real fix is a
**gesture-origin gate**: editor.js reports every document pointerdown
(capture) via `setSelectionGestureOrigin(editor.contains(target))`, and
`handleSelectionAI` evaluates only when the gesture started INSIDE the
editor. A drag-select that ends outside still works; clicking any
toolbar button, menu or panel can never re-surface the popup, mutations
or not.

Tests: statistical-paragraph → table (the field-report case), NOT_TABLE
consultation path, gesture-gated popup scenario incl. DOM mutation.
361 passed, 0 failed.
