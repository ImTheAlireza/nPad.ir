## Verdict

The AI plumbing (proxy, CSP strategy, consent gates, sanitising) is sound. The failures were
**three specific bugs** that combine into exactly the reported symptoms — "the style formatter
doesn't work, and when it works, Apply doesn't work" — plus a handful of dead/inconsistent
wiring around them.

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | **Critical** | **Apply on a selection silently did nothing.** `<dialog>.close()` hands focus back to the AI menu button — *not the editor* — and `document.execCommand()` is a no-op unless the editor holds focus. The selection apply paths never re-focused or restored the selection. | **Fixed** |
| 2 | **Critical** | **Notes over ~30k characters killed the button with no dialog and no error.** The truncation warning callbacks called `fmtWords()` — a function referenced 8 times but *defined nowhere* — and threw a `ReferenceError` *outside* every try/catch, so Smart Formatting / Tone Rewrite died silently. | **Fixed** |
| 3 | **High** | **Oversized full-note runs destroyed content.** Input was truncated to 30k chars, but the apply path did `selectAll` + insert — replacing the *whole* note with a partial rewrite of its first chunk. Output could also be cut mid-HTML (`max_tokens` cap 4000). | **Fixed** — now refuses with a clear message |
| 4 | **High** | **Proxy 403'd legitimate requests on non-standard ports.** The same-origin fallback compared `parse_url($origin)[host]` (no port) against `HTTP_HOST` (often `host:port`) — every AI call failed on `localhost:8787`, preview hosts, and any port-bearing deployment. | **Fixed** |
| 5 | **Medium** | **php-wasm dev/preview can never reach AI providers** (`file_get_contents` has no outbound network), so the AI features were untestable outside production. | **Fixed** — dev-only Node fetch bridge in `dev-server.mjs` |
| 6 | **Medium** | **Markdown answers made "Smart Formatting" a no-op.** Models replying in Markdown despite the HTML-only prompt produced a plain-text blob preview and a plain-text insert. | **Fixed** — minimal Markdown→HTML conversion (still sanitized) |
| 7 | Low | Truncation callbacks were accepted by 8 call sites but the `cleanInput(raw, limit)` signature ignored them — the "trimmed to N words" warning could never fire. | **Fixed** |
| 8 | Low | Dead code: `hasFeatureAck`/`setFeatureAck`/`KEY_FEAT_ACK` never used; header docblock described a per-feature prompt that doesn't exist; loading spinner could leak on unknown selection actions. | **Removed/guarded** |
| 9 | Low | Smart Title / Tone picker read radio inputs via global `document.querySelector` after dialog close — worked only because dialog DOM lingers. | **Scoped to `#appDialog`** |

  admin dashboard panel writes the same `npad:ai-*` keys the app reads.

## Addendum (same day) — field reports: "Unexpected token '<'" and "empty response"

Live probe: `GET https://npad.ir/api/ai-proxy.php` → `{"error":{"message":"Method not allowed"}}` —
the proxy is deployed and executing. Both reported errors therefore come from **what the upstream
provider answers**, which the old code forwarded and parsed blindly:

| Report | Root cause | Fix |
|---|---|---|
| `AI error: Unexpected token '<', "<!doctype"… is not valid JSON` | The proxy forwards the upstream's status **and body** unchanged. A Base URL pointing at a website (wrong path, missing `/v1`, provider homepage) answers **200 + HTML**, and the client crashed in `response.json()`. | Proxy (PHP + dev bridge) now **rejects non-JSON upstream replies** with a 502 naming the content-type and a snippet; client detects HTML replies and shows the Base-URL hint for any status. |
| `AI returned empty response` (site default) | Upstream answered 200 + JSON with no `choices[0].message.content` — reasoning models that spend the whole budget on thinking (`finish_reason: "length"`, `reasoning_content` set), legacy `choices[0].text` shape, or non-OpenAI shapes (Gemini `candidates`). | Client now diagnoses each case with a specific message, surfaces provider error bodies even on HTTP 200, and accepts the legacy `text` shape. |

Also added: `max_completion_tokens` alongside `max_tokens` (OpenAI o-series reject `max_tokens`;
other providers ignore the extra key).

New strings (EN/FA): `ai.html_response`, `ai.empty_length`, `ai.reasoning_only`, `ai.wrong_shape`.

**Deployment note:** npad.ir still serves the pre-fix build. These fixes (and everything above)
take effect only after this branch is merged/deployed.

## Addendum 2 — dashboard test showed "✓ Connected! replied: (empty)" and provider billing errors

Root causes found on the live reports:

1. **The dashboard test button had the old parsing.** `admin/ai-panel.js` kept its own
   `data.choices[0].message.content || '(empty)'` success path — a reasoning model that
   produced zero text was reported as a green "Connected!". The response parser now lives in
   **`assets/js/ai-parse.js`** (single source of truth): `ai.js` (features + settings test) and
   `admin/ai-panel.js` (dashboard test, now an ES module) share it, so an empty reasoning-only
   reply shows *"The model returned only internal reasoning… use a standard chat model"*
   instead of a false ✓.
2. **Provider errors now carry status + code.** Billing failures render as
   `AI provider error (HTTP 402) [insufficient_balance]: Insufficient Balance` — the exact
   provider words plus the account-level context, so the key/account being billed is
   unambiguous. (A "credit" error is the provider's own verdict for the key in use — if your
   custom provider key works but the site default errors, they are different keys/accounts;
   update the site default in the dashboard or keep using your own credentials.)
3. Test requests now send `max_tokens: 32` (+ `max_completion_tokens`) so short replies are
   never truncated by the old 5-token budget.

**Deployment note:** still undeployed — npad.ir serves the pre-fix build until this branch is
merged/released.

## Addendum 3 — the "finish reason length" error with a reasoning model configured

The diagnostic did its job: the screenshot proves the new build is deployed and the provider
answers 200 + `finish_reason: "length"` with empty content — the signature of a
**reasoning/"thinking" model** (deepseek-reasoner, R1/QwQ, Gemini-2.5-thinking, OpenAI
o-series/gpt-5) that spends the feature's small token budget (40–4000) on hidden reasoning
before writing anything. Instead of only explaining, the app now **works with those models**:

- `assets/js/ai-parse.js` gains `requestChatCompletion()` — the one request path used by the
  editor features, the settings test and the dashboard test:
  1. model names that look like reasoning models (`deepseek-reasoner`, `r1/rN`, `o1/o3/o4`,
     `qwq`, `*think*`, `gpt-5`) start with a **2048-token floor** instead of the feature's
     tiny default;
  2. if the reply is still empty-length, it **retries once automatically** with
     `min(16384, max(4096, 8x))` tokens — enough headroom for real thinking;
  3. strict OpenAI reasoning models (o-series, gpt-5) get **no custom temperature** (they
     reject it with a 400).
- The guidance error remains as the final fallback (persistent empty-length after retry).

24 AI-suite checks (346 total) pass, including: retry-succeeds, retry-then-fail,
reasoning-name budget floor, and o3-mini temperature omission.
